## 스폰서 계약·실적과 저장 v17

`finance.sponsor`는 kind(basic/broadcast), remainingWeeks, broadcastDays를 보관한다. 방송 계약은 `signSponsor`가 새 주 경계·주간 중단/이벤트/팀 훈련·기존 계약 상태를 검증한 뒤 4회로 시작한다. `prepareDayFinance`는 실제 방송 선수 수를 전달받아 실적을 복사본에 누적하고 정산 때 수입을 결정한다. 검증에 실패하면 복사본을 반영하지 않으므로 재정/계약 차단에 실적과 잔여 계약이 변하지 않는다. 스폰서 수입은 기본 수입과 중복하지 않으며 급여 우선순위/정수 단위는 유지한다. 정산 후 실적 초기화·잔여 횟수 감소, 4회 완료 시 기본 복귀를 처리한다.

정산 기록에 sponsorKind와 broadcastDays를 넣어 계약 종료 후에도 당시 수입을 검증한다. v1~v16의 기록은 과거 30일 정산에는 legacy/0, 주간에는 basic/0을 추가하며 기존 금액은 보존한다. 현재 저장은 스폰서 상태와 진행 일수별 가능한 실적, 정산 조건에 맞는 수입을 검증한다. basic은 잔여/실적 0, broadcast는 잔여 1~4·주간 실제 실적 상한 56이다. 내 구단 재정에 계약 카드/실적/지급 조건과 정산 이력을 표시한다.

최신 개발 범위(2026-11-08): 사용자 요청으로 스카우팅·협상 확장·AI 자율 운영 확장을 제외했다. 기존 구현의 영입/자동 판매와 AI 명단 정리는 유지하며, 아래 초기 제안과 과거 기록의 추가 운영 계획은 최신 개발 계획을 따른다.

## 새 게임 구단 교체 확인 UI

기존 `confirmReplacement`가 사이트 스타일 native dialog의 Promise를 기다린 후에만 저장과 세계 교체를 진행한다. 현재/저장/새 구단 정보는 HTML 이스케이프하고 저장 실패 시 기존 안내 범위를 유지한다. 취소/Esc는 거절로 처리하며 취소 버튼에 초기 포커스를 둔다. 작업 중 #app이 inert이므로 dialog는 document.body에 추가하고 닫기/열기 실패 시 제거한다. 공용 교체 경로(새 게임/JSON 가져오기/저장 슬롯 교체)에 적용하며 저장 정책과 별도 이어하기 확인은 유지한다.

## 영입 후 8주 판매 제한 (v16)

계약의 `acquiredDay`에 이번 소속의 영입일을 기록한다. 자유계약/구매/AI 영입 계약은 현재 게임 날짜를 사용하며 초기 소속 계약과 구형 저장 이행은 `null`로 대기를 면제한다. `renewContract`의 계약 복사는 이 값을 유지하며 방출/재영입은 새 날짜를 기록한다. 현재 버전은 null 또는 1~현재 게임 날짜의 안전한 정수만 허용하고 누락/미래/잘못된 타입을 거부한다. v1~v15의 계약은 영입일 null을 추가하고 기존 조건/선수/구단 상태를 유지한다.

`saleQuote`가 `56 - (world.day - acquiredDay)`의 양수 여부로 제한을 검증하고 남은 실제 일수와 주 단위 올림 안내를 반환한다. 자동/명시적 거래 모두 같은 견적을 재검증한다. UI는 판매 접기의 제목과 불가 안내에 남은 주를 보여준다. 기존 급여 누적/계약 잔여일 로직과 독립적이며 관전·재계약·단순 저장은 대기 기간을 소비하지 않는다.

## 구단 단위 판매·AI 명단과 자유계약 시장 (v15)

후속 사용자 요청으로 판매 UI의 구단 선택을 제거했다. `sellPlayer(world, playerId)`가 현재 견적을 다시 계산해 첫 구매 가능 구단으로 자동 판매하고 완료 메시지에 구단을 알린다. 명시적 구단 인자는 거래 검증/시뮬레이션용으로 유지한다. 구매 조건·금액·AI 편성 규칙은 동일하다.

`saleQuote`의 구매 조건은 상대 소속 선수 중 한 명보다 세 기본 능력 중 하나라도 높고 자금이 충분한 경우다. 견적은 구매 구단만 제공한다. `sellPlayer`는 리그별 AI 정원(`aiRosterMaximum`: 세계 8명, 나머지 5명)에 따라 필요한 경우 기존 최저 평균 선수를 방출하고 영입 후 평균 상위 5명을 주전으로 정한다. 동률은 기존 순서, 당일 새 영입자는 해당 정리에서 유지한다. 기존 구매 협상에서 후보가 있는 AI 명단이 변경돼도 주전 상위 5명과 계약을 유지하도록 재편성한다. 내 구단의 5+3 규칙과 판매 보호/금액/수동 저장은 유지한다.

저장 v15는 세계 AI에만 후보 정원을 허용한다. v1~v14의 AI는 기존 5명 조건으로 검증하고 상태를 그대로 복원한다. 새 선수 필드는 없으며 세계/다른 리그 정원·계약·주전·중복 소속 검증을 확장한다. `playersScreen`은 소속 필터 입력 없이 자유계약만 추린 뒤 정렬/페이지를 계산한다. 메뉴/제목은 선수 영입이며 시장의 다른 구단 협상 노출을 제거한다. 리그·구단 화면에는 주전/후보를 표시한다. 아래 판매 v14 설명의 특정 선수 대체 조건은 이 규칙이 대체한다.

## 내 선수 판매 초기 구현 (v14)

`transfers.js`의 `saleQuote`가 내 구단 소속·최소 명단·진행 중 팀 훈련/이벤트 보호와 판매 수입 상한을 검증한다. 후보 AI의 같은 포지션 주전 능력과 자금으로 구매 가능한 구단을 계산하고, `sellPlayer`가 현재 견적을 다시 확인한 뒤 공용 `releasePlayer`로 내 명단/계약을 정리한다. 상대 계약 생성까지 검증한 후 자금 이동·상대 선수 자유계약·새 주전/계약을 동기적으로 갱신한다. 기본 이적료 산식은 구매/판매가 같은 내부 함수를 사용한다.

내 구단 화면의 선수별 접기 영역에 금액·구매 구단·판매하기 또는 불가 사유를 표시한다. 성사 시 미저장으로 표시하고 기존 세계 저장 v14에 두 구단과 선수 상태를 함께 보관한다. 별도 저장 필드/버전 변경·자동 저장은 추가하지 않는다. 판매 전 발생 급여/미지급은 기존 재정 장부에 유지하며 날짜/경기 기록/선수 성장 상태는 변경하지 않는다.

## 피로·컨디션과 저장 v14

선수의 `fatigue` 정수(0~100)를 저장하고 컨디션은 `100 - fatigue`로 계산한다. `player-condition.js`는 상태 검증·행동 피로 누적/회복·경기 페널티를 담당한다. `trainPlayers`가 실제 행동일 시작 시 기본 체력으로 피로를 계산하고, 이후 기존 행복도/경험치를 처리한다. 날짜·재정·계약 검증을 통과한 날만 호출되므로 일정 차단에는 피로가 변하지 않는다. 체력 훈련으로 80에 도달한 날의 완화는 소급하지 않는다. 정산/관전에서는 피로를 다시 처리하지 않는다.

`effectiveStats`는 에임·지능에 행복도와 피로 보정을 합산하며 체력에는 기존 행복도 보정만 적용한다. 경기 선수는 생성 시 복사한 능력을 유지한다. v14에는 피로 정수 검증이 필수이며 v1~v13에는 0을 추가하고 기존 모든 필드와 과거 결과를 보존한다. 컨디션을 별도 저장하지 않아 피로와의 불일치를 방지한다. [피로 작업 기록](../work-logs/2026-11-08/2026-11-08-20-player-condition.md)이 현재 피로 규칙의 기준이다.

## 잠재력·성장 속도와 저장 v13

아래 v13은 성장 구현 당시의 기록이며 현재 버전은 v14다.

`player.development`에 능력별 `potential`과 정수 백분율 `growthRate`(80/100/120)를 저장한다. 세계 시드와 선수 ID에서 별도 난수를 생성해 기존 선수 생성·행동·이벤트 난수를 소비하지 않는다. 현재 능력보다 잠재력이 낮으면 현재 능력으로 보정한다. 새 세계와 v1~v12 변환 모두 같은 배정 함수를 사용하며 v13에는 필수 검증한다. 현재 능력·잔여 경험치·계약·재정은 보존하며 잠재력에 이미 도달한 기존 잔여 경험치도 소급 제거하지 않는다(기존 99 능력/경험치 0 규칙 유지).

개인 훈련은 하루 10 경험치에 성장 배율을 적용한다. 팀 훈련은 모드·승패·KDA로 계산한 총량에 성장 배율을 한 번 곱해 반올림한 뒤 정수 경험치를 무작위 분배한다. 공용 `gainExperience`는 실제 지급량을 받아 능력별 잠재력에서 멈춘다. 상한에 배정된 경험치는 다른 능력으로 재추첨하지 않는다. 완료한 팀 보상에는 당시 `growthRate`, 이벤트 이력에는 당시 `statLimit`을 저장해 이후 능력 변화로 과거 결과를 재계산하지 않는다. 이전 보상은 100%, 이전 이벤트는 상한 99로 읽는다. 이벤트 상승으로 새 상한에 도달하면 잔여 경험치를 0으로 하되, 이미 상한인 선수에게 변화 없는 이벤트가 발생하면 보존한다. 이벤트 하락·휴식 경험치 감소·행복도 경기 보정은 기존 계산을 유지한다.

전체 선수/구단 명단의 성장 정보 접기와 내 구단 능력·경험치 표에서 잠재력과 성장 배율을 공개한다. 영입 가격·급여에는 잠재력/성장 배율을 직접 반영하지 않는다. [작업 기록](../work-logs/2026-11-08/2026-11-08-19-player-development.md)을 현재 기준으로 사용하며 아래 구형 성장/저장 설명은 해당 버전의 이력이다.

## 초기 환경 확인

초기 조사 당시 기술 스택은 Node.js, JavaScript, HTML, CSS였고 규칙 문서 4개만 있었다. Node.js v24.21.0, npm.cmd 11.19.0을 확인했다. 첫 구현에서 Vite 8.3.6과 package.json·lockfile·src·index.html을 추가했다. PowerShell에서는 npm.cmd를 사용한다. git은 현재 PATH에서 찾을 수 없으며 버전 관리 설정은 이번 작업에 포함하지 않았다.

## 기술 선택 비교

| 항목 | 추천 | 대안 및 판단 |
|---|---|---|
| 프론트엔드 | JavaScript ES modules + HTML + CSS | React는 많은 관리 화면에 도움이 될 수 있지만 첫 화면 구현에 필수는 아니다. 도입 시 사용자 승인 필요 |
| 개발·빌드 | Vite 추가 | 개발 서버와 정적 빌드 명령을 제공한다. Node 자체 정적 서버도 가능하지만 도구 코드를 직접 관리해야 한다 |
| 타입 | JavaScript 유지 | TypeScript는 데이터 실수 예방에 유리하지만 스택 변경이므로 현재 도입하지 않는 안 |
| 관리 UI | DOM·시맨틱 HTML | 표·입력·키보드 조작에 적합 |
| 경기 지도 | Canvas 2D (경기 단계) | 도형 중심 지도에 적합하다는 설계 판단. Phaser 도입은 현재 필수 근거가 없다 |
| 상태 | 단일 게임 상태 + 명시적 상태 변경 함수 | Redux 등 추가 라이브러리는 초기 요구에 불필요 |
| 장기 저장 | IndexedDB + JSON 백업 (저장 단계) | 구조화된 비동기 저장에 적합. localStorage는 소량 환경 설정 용도로 제한 제안 |

초기 화면·저장과 58팀·600명의 초기 세계는 사용자 승인 범위에서 구현했다. IndexedDB 1개 슬롯에 현재 세계 전체를 저장하며 추가 의존성은 없다. 이동·시야·교전·폭탄·구매·MR12·연장전은 구현했고 세계의 시즌·성장·경영 행동은 **후속 제안**이다. 범용 저장 어댑터, 종목 플러그인, 이벤트 버스, 범용 엔진 기반은 선행 구현하지 않는다.

Node.js는 개발 도구 실행용이며 게임은 브라우저에서 실행한다. 첫 구현에는 서버·계정·클라우드 저장이 없다. 설치 시 npm 레지스트리에서 Vite 8.3.6의 Node 조건 ^20.19.0 또는 >=22.12.0을 확인했고 현 Node와 호환됨을 확인했다. Vite 버전을 고정하고 lockfile을 생성했다.

## 첫 구현에 필요한 책임 분리 제안

src/main.js는 화면 전환·메모리 상태·입력 처리를, src/ui/screens.js는 화면 표시를 담당한다. src/config/game.js에 게임 표시 이름·초기 조건을 두고 src/game/create-club.js에서 이름 검증·구단 생성을, src/data/starter-players.js에서 초기 가상 명단을 관리한다. src/styles.css는 공통 UI 스타일이다. UI에서 임의로 구단을 수정하지 않고 생성 결과를 진입점에서 교체한다.

메뉴 → 새 게임 안내 → 구단 생성 → 초기 구단 정보 화면을 제안한다. 화면 입력 중 임시 데이터와 확정된 구단 데이터를 구분하고 생성 실패 시 기존 상태를 보존한다. 첫 단계는 메모리에만 유지하며 새로고침하면 초기화된다. 저장 버튼이나 이어하기를 실제로 동작하는 것처럼 표시하지 않는다.

## 팀 연습 화면 높이 배치

최신 확대는 지도 요소만이 아니라 팀 연습 section 전체를 표시 영역에 고정해 상단 시작/스킵/배속·점수와 패널을 함께 사용한다. 공용 패널 툴바는 열린 패널과 분리하고 패널이 모두 닫히면 지도 열을 전체 가로 공간으로 확장한다. 확대 중 옆 패널 폭을 제한하며 조작 요소·구매 상태·기록은 복제하지 않는다. 경기 구매 명칭은 장비 구매로 바꿨다. [확대 조작 기록](../work-logs/2026-11-08/2026-11-08-18-expanded-match-controls.md)을 따른다. 아래 지도 단독 확대 설명은 이전 단계다.

확대 후에도 지도가 작게 남는 후속 문제는 캔버스 자체의 현재 크기 대신 지도 영역 getBoundingClientRect를 기준으로 해결한다. 맵 비율에 맞춘 CSS width/height를 먼저 지정하고 DPR을 곱한 렌더링 크기는 별도로 설정한다. ResizeObserver는 지도 영역을 관찰해 확대·복귀·창 크기 변경에 맞춰 다시 계산한다.

후속 수정에서 경기 규칙은 닫기 버튼·Esc를 제공하는 별도 dialog로 옮겼다. 지도 우측 상단 확대 버튼은 표시 영역 대부분을 지도로 사용하고 버튼 재클릭·Esc로 복귀한다. 경기 상태는 변경하지 않으며 화면 종료 시 창/확대와 이벤트 리스너를 정리한다. [규칙/확대 작업 기록](../work-logs/2026-11-08/2026-11-08-17-practice-rules-expand.md)을 따른다.

팀 연습 화면에서만 앱 높이를 브라우저 뷰포트에 맞추고 상단 조작/점수와 지도·옆 패널을 배치한다. 구매는 기본으로 열고 수동 전략·자동 전략·구매·경기 내용을 한 패널씩 전환한다. 긴 내용은 패널 내부에서 스크롤하며 규칙·보상·선수 상세는 details로 접는다. 작은 화면은 지도/패널을 위아래로 나누고 지도는 3:2 비율을 유지해 기존 클릭 좌표 변환을 보존한다. 다른 구단 화면의 페이지 스크롤과 경기 엔진/저장은 변경하지 않는다. [작업 기록](../work-logs/2026-11-08/2026-11-08-16-practice-viewport.md)에 사용자 화면 확인 절차를 기록한다.

## 주간 선수 이벤트 15종과 저장 v12

world.playerEvents에 별도 randomState·현재 주간 계획·최근 선택 결과 20건을 보관한다. UI 주간 진행은 이벤트를 활성화하며 첫 날짜가 성공한 뒤 주당 60% 확률로 최대 1건과 발생 시점을 추첨한다. 실제 발생 시 현재 소속 선수 중 대상을 선택하고 결과 판정 난수를 고정한다. 팀 훈련 경험치·경기·세계 생성 난수와 분리한다. 내부의 비대화식 날짜/주간 계산은 기존 동작을 유지한다.

주간 계획에는 시작/종료 날짜와 팀 훈련 여부가 있어 계약 차단·이벤트·저장 복원 후 같은 주를 재개한다. 선택 중 날짜/행동 변경·팀 훈련 시작·대상 방출을 막고, 선택 후 실제 남은 기간만 처리한다. 마지막 날짜에 이벤트가 발생하면 남은 기간 0으로 마무리하고 새 주를 소비하지 않는다. 팀 훈련은 그 다음에 참가 세션을 생성한다.

비용/수입·행복도는 확정, 능력은 선택별 확률로 기본 수치 ±1을 반영한다. 돈과 상한을 먼저 검증해 실패 시 원본을 유지한다. 행복도 0~100·능력 1~99·99 도달 시 해당 잔여 경험치 0을 지킨다. 선택 결과는 실제 전후 값으로 보존하고 예정/대기/처리 상태를 검증해 재추첨·중복 반영을 막는다.

구단 이벤트 패널의 native dialog에 양쪽 효과와 확률을 미리 표시하고 자금 부족 유료 수락을 막는다. 선택 전 저장과 나중에 선택을 제공하며 닫거나 다른 화면에 갔다 와도 같은 대기를 재개한다. 결과 목록은 대상 이름을 HTML 이스케이프한다. 기존 수동 저장을 유지하며 v1~v11은 기존 세계를 보존하고 이벤트만 빈 상태로 추가한다. [작업 기록·2·3번 통합 체크리스트](../work-logs/2026-11-08/2026-11-08-15-player-events.md)를 따른다.

## 행복도·행동 반복·장기 휴식과 저장 v11

선수별 morale에 happiness(0~100, 초기 70), lastAction, consecutiveDays, lastDay를 저장한다. 실제 진행한 내 소속 선수 행동만 갱신하며 AI/미소속 선수는 멈춘다. 기록이 없는 상태는 null/0/null 조합으로 검증하고 기록이 있으면 허용된 행동·지난 수행 날짜·가능한 연속 기간인지 확인한다. 신규 영입도 기존 선수 상태를 사용해 재영입 초기화를 막고 수행 날짜 공백은 연속 행동을 끊는다.

trainPlayers의 성공한 날짜 처리에 행복도를 연결한다. 개인/팀 훈련은 첫 7일 유지, 방송은 첫 7일 +1/일이며 같은 비휴식 행동 8~14일 -1/일, 15일부터 -2/일이다. 휴식은 1~7일 +2/일, 8~14일 +1/일·능력별 경험치 -2/일, 15일부터 행복도 유지·각 경험치 -3/일이다. 경험치 0 하한과 기본 능력 보존을 적용한다. 계약/금액 차단 전에 행복도나 기록을 변경하지 않는다.

createPractice가 현재 행복도에 따른 세 경기 능력을 복사한다. 90 이상 +3 / 75~89 +1 / 45~74 0 / 25~44 -2 / 24 이하 -4이며 1~99로 제한한다. 기본 세계·가격·경험치는 수정하지 않고 기존 경기에는 중간 재적용하지 않는다. 체력 경기 계산의 별도 확장은 없다.

v1~v10은 행복도 70·빈 기록으로 변환하고 기존 세계를 보존한다. 과거 행동은 소급하지 않는다. 저장/백업은 기존 수동 정책을 유지한다. 선수 능력/행동 패널에 행복도·임시 적용 능력·반복 상태와 효과를 표시한다. [작업 기록](../work-logs/2026-11-08/2026-11-08-14-player-happiness.md)에 수치와 확인 절차를 기록한다.

## 계약·구단 재정 주 단위 전환과 저장 v10

신규 계약은 내부 84일(12주), 재계약은 28/84/168일(4/12/24주)이다. 일별 행동·중간 만료·주간 중단/재개 계산을 보존하고 계약 UI는 약정/잔여 기간과 급여를 주 단위로 표시한다. 기존 월급 필드는 주급 산출 기준으로 보존하며 실제 주급은 해당 값의 1/4이다.

src/rendering/practice-map.js는 상태를 읽어 지도를 그리는 책임만 가진다. src/ui/practice-screen.js는 재생·일시정지·초기화·선택·requestAnimationFrame과 Canvas 크기를 연결한다. 프레임 사이 경과 시간을 누적해 필요한 고정 단계만 계산하며 화면 크기는 계산 좌표를 바꾸지 않는다. 백그라운드 탭으로 전환하면 일시정지하고 돌아온 뒤 사용자가 계속할 수 있다. 화면 이탈 시 RAF·ResizeObserver·이벤트 리스너를 해제한다.

선수는 파랑/보라 원형·번호와 전방 방향선으로 표시한다. 선택은 지도 클릭 또는 목록으로 가능하고 시야 다각형·테스트 경로·목적지·감지 상대를 표시한다. 관전자는 양 팀을 모두 보며 금색 외곽 원이 실제 선택 선수의 감지 결과다. 연습 상태는 저장 v2와 분리하고 원래 세계·구단·선수를 변경하지 않는다.

AI는 경로·충돌·가림·시야 다각형·양 팀 전원 도착·시간 분할 일치·세계 원본 보존을 Node 테스트로 확인했다. 실제 Canvas·입력·일시정지·화면 이탈/재진입 동작은 [맵 작업 기록](../work-logs/2026-11-07/2026-11-07-05-map-movement-vision.md)의 사용자 확인 사항이다.

## 한 라운드·폭탄 구현

src/config/round.js는 사용자 승인한 설치 전 2,300틱(115초)·설치 80틱(4초)·해체 140틱(7초)·폭발 800틱(40초)을 정의한다. src/simulation/round.js는 진영별 시작 위치와 목표 이동·운반/낙하/회수·행동 진행·승패를 담당한다. 상태는 기존 연습 상태 안의 round로 분리하고 교전 전용 모드에는 추가하지 않는다. 구매·MR12·저장 스키마는 변경하지 않는다.

공격은 선택 사이트로 이동한다. 사용자 피드백 수정으로 수비는 설치 전 A/B 주변을 순찰하고 실제 아군 시야로 감지한 적 위치에 대응한다. 공유 위치는 마지막 관측 5초 후 만료하며 보이지 않는 현재 위치를 따라가지 않는다. 설치 후 공격은 폭탄 주변 경계 경로를 순환하고 수비는 가까운 생존자 한 명이 해체에 접근하며 나머지는 경계한다. 담당자는 생존 중 유지하고 사망 시 거리·ID 순으로 다시 선택한다. 경제 경기에서는 기존 담당의 예상 해체가 늦고 다른 선수가 가능하면 담당을 교대한다. 경로 책임은 src/simulation/round-movement.js에 분리했다. 이는 현재 정지 문제를 해결하는 기본 행동이며 전술 편집·포지션별 전략 전체를 구현한 것은 아니다.

공격팀도 ID별 실제 관측 위치를 5초 동안 공유한다. 현재 구역 수비 3명 이상·다른 구역 1명 이하 관측 상태가 40틱 지속되고 공격 생존 3명 이상이면 사이트 전환을 검토한다. 운반자의 변경 경유점 경로·설치 80틱·여유 100틱이 제한 시간 안에 들어갈 때 라운드당 한 번 전환하고 가까운 중간점으로 합류한다. 수동 명령·설치 진행·폭탄 낙하/설치 후는 제외한다. `initialSiteName`은 사용자가 처음 고른 사이트를 유지해 다음 라운드에 복구한다. 자동 진입 중 같은 방향 아군을 가까이 따라가면 이동 예산을 60%로 낮추되 운반·수동·최종 진입·마감 10초 이내는 제외한다. 경계 목적지는 우선순위가 앞선 아군 목표와 몸체 합계+12 이상 떨어진 후보를 우선하고 없으면 기존 후보를 사용한다. 기존 벽/몸체 회피를 유지한다. 검증과 범위는 [사이트 전환·간격 기록](../work-logs/2026-11-09/2026-11-09-15-rotation-spacing.md)을 따른다.

경제 경기의 설치 후 수비는 벽 우회 경로·자기 이동 속도·폭탄 접근 범위·진행 중인 해체의 잔여 시간을 계산한다. 누구도 마감 전에 완료하지 못할 것으로 예상되면 후퇴한다. 해체 가능 시간이 있어도 마지막 수비수가 HP 45 이하·상대 생존 3명 이상·최근 5초 내 폭탄 240 단위 안의 적 2명 이상 관측·잔여 17초 이하·보존할 장비 보유인 경우 불리한 재탈환을 포기한다. 폭탄에 이미 접근했거나 해체 중이면 이 승산 조건으로 포기하지 않는다. 장비 초기화 직전과 상대 매치 포인트에서도 가능한 해체를 계속한다. 관측 정보가 만료되거나 인원이 바뀌면 재평가한다. 후퇴 목적지는 접근 가능한 시작 지점 중 폭탄/관측된 적과의 거리 및 벽 엄폐를 고려해 고르고 기존 충돌 회피로 이동한다. 현재 숨은 적 위치·체력·장비는 사용하지 않는다. 이는 설치 후 수비의 제한된 보존 판단이며 공격 중 포기·구매 전략·사이트 변경은 포함하지 않는다. 상세 검증은 [장비 보존 기록](../work-logs/2026-11-09/2026-11-09-14-equipment-saving.md)을 따른다.

사이트 안 운반자와 폭탄 12 단위 이내 해체 담당자는 각각 설치·해체를 수행한다. 목표 행동은 이동·사격과 동시에 하지 않는다. 현재 볼 수 있고 자기 무기 사거리 안에 있는 유효 교전 표적 또는 최근 20틱의 실제 피격이 있으면 중단하고 진행을 초기화한다. 단, 마감 전에 현재 행동을 완료할 수 있지만 다음 틱부터 처음 시작하면 완료하지 못하는 구간은 설치·해체를 우선한다. 범위 이탈·사망은 계속 중단 조건이며 마감과 같은 틱 완료가 실패하는 규칙은 유지한다. 상세 검증은 [설치·해체 작업 기록](../work-logs/2026-11-09/2026-11-09-13-objective-priority.md)을 따른다. 낙하 위치 12 단위 이내 생존 공격수가 ID 순으로 회수한다. 모든 이동은 기존 벽·경로 계산을 사용하며 순찰은 목적지 도착 시 다음 지점으로 이어진다.

50ms 틱마다 목표 행동 결정 → 이동 → 교전·피해 → 라운드 처리를 수행한다. 교전 계산은 라운드 모드에서 자체 전멸/60초 종료를 적용하지 않는다. 라운드 처리는 폭탄 낙하 → 폭발 → 전멸 → 설치 전 시간 만료 → 회수 → 설치/해체 완료 순이다. 폭발과 해체 완료, 설치 제한과 설치 완료가 같은 틱이면 마감 시각을 우선하며 해당 틱 사망자는 행동을 완료하지 못한다.

설치 전 공격 전멸(양 팀 동시 전멸 포함)은 수비 승리, 수비 전멸과 공격 생존은 공격 승리다. 설치 후 공격 또는 양 팀 전멸은 폭탄 판정까지 계속한다. 폭발은 공격 승리, 해체·설치 전 시간 만료는 수비 승리다. 종료 후 계산과 이벤트 추가를 막는다. 결과는 연습에만 남기고 세계·구단·선수 원본을 변경하지 않는다.

한 라운드 모드는 진영·A/B 선택, 운반자·폭탄 위치·잔여 시간·설치/해체 진행·종료 이유를 표시한다. 설정 변경·초기화는 같은 시드로 다시 시작한다. 당시 라운드 14개를 포함한 총 52개 Node 테스트, JavaScript 문법 검사와 빌드를 통과했다. 브라우저 확인은 [라운드 작업 기록](../work-logs/2026-11-07/2026-11-07-07-round-bomb.md)에서 진행한다. 현재 기본 모드는 아래 구매·라운드 모드다.

HP 45 이하 또는 전진 감시의 시야 내 적 2명 이상이며 즉시 사격 가능한 아군보다 많으면 해당 라운드에 후퇴를 유지한다. 전진 감시는 뒤 아군 합류 지점으로, 기본 감시·사이트 방어는 벽 뒤 지점으로 물러난다. 후퇴 중에는 정지 교전보다 이동을 우선하며 도착 후 경계한다. 설치 후 기존 해체·지원 경계를 우선하고 새 라운드에는 후퇴 상태를 초기화한다. 위험 기준은 현재 행동 검증용 수치다.

round-movement는 설치 전 수동 경유점과 마지막 시선을 사용한다. 기존 정지 교전·피격 반응은 유지하며 폭탄 낙하/설치 후에는 자동 폭탄 행동이 우선한다. 운반자의 경로 완료 여부는 라운드 동안 유지해 사이트로 이동한 뒤 마지막 수동 지점으로 돌아오는 반복을 막는다. 운반자는 경로 완료 후 설치 사이트로 이동하고 설치 후 공격 경계/수비 해체는 기존 자동 배치를 따른다.

화면의 접이식 수동 편집기에서 내 팀 선수·편집 진영·기간·지도 조작을 고른다. 초안 경유점/시선은 경로 적용 전까지 경기 설정을 바꾸지 않는다. 지도는 같은 BFS로 벽을 우회하는 경로·번호·마지막 방향을 표시한다. 반대 진영 경로도 그 진영의 시작점 기준으로 미리 편집할 수 있다. 전투·일반 일시정지 중에는 편집을 잠그며 감독 타임아웃에서만 진행 중 편집을 연다. 설정은 연습 화면 안에서만 유지하고 저장 스키마·구단 원본은 바꾸지 않는다.

## 선수 몸체 겹침 방지 구현

src/simulation/actor-movement.js는 이동 단계에서 생존 선수 반지름 합으로 원형 몸체 충돌을 계산한다. 각 미세 이동 구간과 상대 중심 사이 최단 거리를 검사해 빠른 이동도 관통을 막는다. 벽 판정은 기존 moveWithCollision을 재사용하며 정지·설치/해체 중인 선수를 밀지 않고 사망자는 장애물에서 제외한다. ID 정렬 후 매 틱 시작 순서를 순환해 입력 배열 순서에 의존하지 않는다.

직접 이동이 막히면 주변 방향을 검사하고 필요하면 10틱 동안 짧게 양보한다. 중간점이 20틱 이상 진행되지 않으면 findPath에 현재 아군·보이는 적·직접 접촉한 적을 장애물로 전달해 우회한다. 숨은 먼 적의 현재 위치를 사용하지 않는다. 경로 재탐색 후에도 모든 실제 이동 구간에서 충돌을 다시 검사한다. 새 라운드에는 통행·우회 상태를 초기화한다.

점유된 일반 목표는 인접한 안전 위치에서 crowdedGoal로 도착 처리하고 reachedDestination을 자동 공격·수동 경로 진행에 공유한다. 내부 경로점은 다음 구간이 벽을 통과하지 않을 때만 가까운 통과를 허용한다. 운반자의 최종 설치 접근·회수·해체는 몸체 간격만으로 완료 처리하지 않으며 기존 실제 위치·시간 조건을 적용한다. 선수 상세는 통행 대기와 벽 막힘을 구분한다.

추가 충돌 검사 6개를 포함해 총 128개 테스트·JavaScript 53개 문법 검사·39개 모듈 Vite 빌드가 통과했다. 실제 전술 8조건의 매 틱 벽/몸체 비겹침, 같은 수동 목적지, 양 팀 우회·재현, 기존 전원 도착과 회수 후 설치를 확인했다. 브라우저 확인과 밸런스 재평가는 [작업 기록](../work-logs/2026-11-07/2026-11-07-15-player-collision.md)에 구분한다.

## 후속 경기 시뮬레이션 제안

배속·렌더링 빈도에 따라 결과가 달라지거나 DOM 의존으로 계산을 검증하지 못하는 문제를 막기 위해, 현재 고정 간격 계산·화면 분리를 이동·시야·교전·라운드·구매·MR12에 적용했다. 타임아웃의 계산 정지는 구현했으며 아래는 구단 결과 정산·배속·스킵까지 확장하는 후속 제안이다. 기본 경기 종료까지 구현했지만 시즌 반영·고급 관전 흐름은 아직 포함하지 않는다.

입력은 맵 판정 데이터·선수 능력·전술·무기·초기 경기 상태·난수 시드다. 계산은 라운드 준비/구매 → 이동 의도 → 충돌·시야 → 교전 의도 → 사격·피해 → 폭탄·시간 → 라운드 종료 → 진영 교대·경기 종료 순서의 명시적 처리로 제안한다. 동시 교전 편향을 줄이기 위해 의도 수집과 결과 적용을 나누고 안정적인 처리 순서를 정의한다. 순서와 틱 간격·산식은 프로토타입 단계에서 검증·승인한다.

시야는 거리·방향·벽 가림, 명중은 무기·거리·이동·능력·상태의 영향을 받아 계산하는 안이다. 전체 팀 능력 합계로 승패를 선추첨하지 않는다. 경로는 맵의 이동 가능 영역에서 계산하고 렌더러가 벽을 임의 추가하지 않는다. 설치·해체·전멸·시간 만료의 우선순위를 규칙으로 명시한다. 특히 설치 후 수비 측 전멸과 공격 측 전멸은 폭탄 상태에 따라 다르게 처리해야 한다.

출력은 현재 경기 상태와 명중·피해·사망·설치·해체 같은 이벤트다. 통계와 하이라이트는 실제 이벤트로부터 생성한다. 렌더러는 상태를 읽어 보간·그리기만 수행한다. 1배·2배·4배·스킵은 수행할 계산량이나 표시 빈도만 조절하며 같은 입력과 시드에서는 같은 결과여야 한다. 스킵에서도 라운드 사이·타임아웃 결정 지점을 지켜야 한다.

경기 상태는 장기 구단 상태에서 분리하고 경기 종료 시 결과를 한 번만 반영한다. 중복 정산 방지를 위해 경기 ID와 반영 여부를 관리하는 안을 제안한다. Web Worker는 계산 때문에 UI가 멈추는 문제가 측정되면 도입 여부를 결정한다. 현재 10명이라는 이유만으로 성능을 보장하지 않는다.

## 초기 세계 구현 및 후속 데이터 구조

현재 세계는 seed, playerClubId, clubs, players로 구성한다. clubs는 id·name·leagueId·discipline·balance·playerIds를 가지며 선수 원본은 players에만 둔다. playerIds 참조로 구단 명단을 조회하고 참조되지 않은 310명은 자유계약이다. 리그 정의·정원은 src/config/world.js 한 곳에서 관리하며 저장 데이터에는 구단별 leagueId를 기록한다.

초기 생성은 구단당 5명과 자유계약을 포함한 총 600명이다. 생성용 시드와 고정 난수 계산으로 같은 입력은 같은 세계를 만든다. 새 게임은 임의 시드, 구형 저장 변환은 정규화된 구단 내용에서 계산한 고정 시드를 사용한다. AI 팀명은 독자적인 단어 조합, 선수는 가상 이름·별명으로 생성하며 기존 선수 ID와 충돌하는 생성 ID는 건너뛴다.

승인된 초기 능력 범위는 PC방 30~54, 시 40~64, 도 50~74, 전국 60~84, 전세계 70~94, 자유계약 20~89다. 기존 플레이어 선수 능력은 그대로 보존한다. 이 범위는 생성용 임시 분포이며 가져오기에서는 1~99 유효성을 검사한다. 세계 검증은 58팀·600명·리그별 정원·5명 명단·ID 유일성·존재하는 참조·중복 소속 금지·플레이어 PC방 소속을 검사한다.

리그·구단 화면은 리그 선택과 구단별 5인 명단을 제공한다. 전체 선수 화면은 전체/자유계약/구단별 소속 필터와 30명 단위 페이지 이동을 제공한다. 필터·선택 화면 상태는 게임 데이터와 분리된 UI 상태이며 세계 데이터는 조회로 변경하지 않는다. 명단 표 렌더링은 내 구단·타 구단·전체 목록에서 공통 구현을 사용한다.

## 저장 단계 구현

2026-11-07 사용자가 IndexedDB 1개 슬롯·창단 자동 저장·수동 저장·이어하기·JSON 백업·덮어쓰기 확인을 승인했다. src/storage/save-data.js는 현재 구단의 저장 형식 생성과 검증, src/storage/save-store.js는 IndexedDB 입출력, src/main.js는 UI와의 연결을 담당한다. 추가 라이브러리나 서버는 도입하지 않았다.

데이터베이스 이름은 가제 표시명과 독립된 eco-to-hero, DB 버전은 1, object store는 saves, 저장 키는 active다. 저장 레코드는 revision과 data를 가진다. 현재 data는 format: eco-to-hero, schemaVersion: 2, savedAt, world를 포함한다. world 전체를 저장하고 불러와 구단·선수·시드를 보존한다. DB 버전과 게임 저장 스키마 버전은 별개다.

schemaVersion: 1과 club을 가진 구형 저장·백업도 기존 검증으로 읽는다. 구단명·자금·선수 ID·이름·능력을 보존해 세계를 메모리에서 생성한다. 이어하기는 기존 IndexedDB 데이터를 덮어쓰지 않고 미저장 표시와 변환 안내를 제공한다. 사용자 수동 저장 시 v2로 교체한다. 구형 JSON 가져오기는 기존 교체 확인·자동 저장 정책에 따라 변환된 세계를 v2로 저장한다. 지원 범위 밖 스키마는 계속 거부한다.

창단과 정상 JSON 가져오기 확정 시 자동 저장하고, 구단 화면에 수동 저장·백업 내보내기·가져오기를 제공한다. 앱 시작 시 슬롯 존재를 확인하고 사용자가 이어하기로 불러온다. 기존 현재 구단 또는 저장이 있으면 구단명을 알리고 교체를 확인한다. 취소·검증 실패 시 기존 구단과 저장을 유지한다.

읽기 확인과 실제 쓰기 사이의 다른 탭 변경은 readwrite 트랜잭션 내부의 revision 비교로 감지해 거부한다. 저장 성공은 요청 success가 아닌 트랜잭션 complete에서 판정한다. 저장소 열기 지연·사용 불가·중단·용량 또는 권한 문제는 실패로 알린다. 창단·가져오기 후 저장에 실패하면 새 구단을 현재 창 메모리에 유지하고 JSON 백업을 안내한다. 변경 충돌은 현재 구단 교체 전에 거부한다. 실제 저장소가 변경되는 단계와 UI 상태 교체를 구분했다.

JSON 파일은 최대 1MB이며 UTF-8 바이트 수로 제한한다. 게임 식별자·지원 스키마 버전·시간과 v1 구단 또는 v2 세계의 필드·참조를 검증한다. 허용된 필드만 새 객체에 복원해 임의 속성을 합치지 않는다. 가져온 이름·별명·구단 문자열은 HTML 이스케이프 또는 textContent로 표시한다. 전체 세계의 보기 좋은 JSON 내보내기도 용량 제한 이내임을 테스트했다.

저장은 브라우저·프로필·접속 origin별로 분리된다. http://127.0.0.1:5173과 localhost 또는 다른 포트는 서로 다른 저장소다. 브라우저 데이터 삭제·비공개 모드·용량 제한에 대비해 JSON 백업을 안내한다. 다운로드 버튼은 브라우저에 파일 다운로드를 요청하며 실제 파일 보관은 사용자가 확인한다.

Node 기본 테스트로 JSON 검증과 저장 이벤트 처리를 확인한다. 이벤트 처리는 테스트용 API 경계에서 검사하며 실제 브라우저 저장·권한·파일 다운로드 성공을 대체하지 않는다. 실제 기능 확인 절차는 [저장 작업 기록](../work-logs/2026-11-07/2026-11-07-03-save-and-load.md)에 있다.

## 검증과 사용자 역할

선수 표시 이름은 별도 이름 데이터와 전용 난수로 생성한다. 기존 세계의 능력·배정·경기 난수를 유지하며, 저장 v4의 선택적 `playerIdentityVersion: 2`로 일회성 이름 갱신 여부를 보존한다. 필드 없는 기존 세계는 복원 시 이름·닉네임만 변경하고 명시적 저장 전에 슬롯을 덮어쓰지 않는다. 자세한 범위는 [이름 작업 기록](../work-logs/2026-11-08/2026-11-08-05-player-identities.md)을 따른다.

## PC방 정규 시즌 기반 구현

사용자가 1단계 일정·순위·저장부터 진행하도록 결정했다. `src/game/pc-season.js`는 독립 난수의 원형 대진으로 PC방 8팀 1회전·7주·28경기를 생성한다. `world.pcSeason`에 구단 ID·주차별 대진·확정 결과의 양 팀 라운드 점수를 저장하고 순위는 매번 결과에서 계산한다. 결과 반영은 MR12와 반복 연장 종료 점수만 받으며 중복 지급/결과 변경·안전 정수 초과를 막는다. 실제 경기 실행은 이 단계에 포함하지 않는다.

`src/ui/season-screen.js`는 정규 시즌 메뉴의 순위·주차별 일정 조회를 제공한다. 저장 v24는 이전 세계를 보존하고 시즌이 없을 때만 미진행 시즌을 고정 보충한다. 최신 저장의 시즌 누락/중복 대진/중복 출전/불가능한 결과는 거부한다. 주간 날짜·훈련/이벤트·공식 보상·스폰서 실적은 아직 연결하지 않았다. 경기장/트로피는 사용자 결정대로 보관만 하고 화면에 넣지 않았다. ## 세계 조별리그 — 2026-11-13 승인·v38

`world-groups.js`는 전국 최종 2팀의 진출·세계 14팀 고정 추첨·4개 조·24개 BO3 대진·조별 순위와 8팀 판정을 담당한다. 조별 상태는 `worldSeason`에 별도 보관하며 기존 국내 시즌은 변경하지 않는다. BO3 맵 선택·완료 맵·퍼즈·기권은 기존 공통 함수를, 조별 동률은 조마다 구분한 ID로 기존 BO1 재동률 결정을 재사용한다.

현재 시즌 선택은 세계→전국→도→시→PC방 순서다. 공식 경기·주간 일정·스폰서는 이 선택을 따르고 누적 기록은 보관한 다섯 리그의 영수증을 합산한다. 세계의 조별 종료 시 국내 플레이오프 정산이나 스폰서 종료가 실행되지 않도록 국내 설정에 속하는지 확인한다. 내 시리즈 종료 뒤 AI 7시리즈를 같은 경기 엔진으로 계산하고 마지막 하루를 정산한다.

v38 검증은 고정 참가/조편성·주별 대진/맵·순차 진행·조별 결정전·활성 경기/명단·주간 준비와 정산 상태를 복원해 비교한다. 구버전에는 `worldSeason:null`만 보충한다. `serializeBackup`은 동일한 검증 데이터를 먼저 들여쓰기 JSON으로 만들고 1MB를 넘으면 공백 없는 JSON으로 내보낸다. 1MB 가져오기 제한과 모든 경기/선수 기록은 유지하며 IndexedDB 저장 형식도 같다. 50~51주 순위별 리그·BO5는 이번 상태에 미리 생성하지 않는다. [세계 조별 작업 기록](../work-logs/2026-11-13/2026-11-13-12-world-groups.md).

v39에서는 `worldSeason.ranked`에 순위별 참가 두 그룹·12개 BO3·BO1 결정전을 별도 보관한다. `world-ranked.js`는 기존 4팀 조별 대진 배치에서 참가자를 바꿔 새 ID/맵을 만들고, 진입 조건과 순위별 저장 순서를 검증한다. 순위·동률 재경기·진출 판정은 기존 세계 함수를 재사용한다. 현재 진행 조회는 순위별 상태를 우선하고 보관된 조별 결과 조회는 그대로 유지한다.

순위별 대진의 `round`는 1~3이며 주차는 4/4/5(연간 50/50/51주)다. 같은 회차 AI 결과 뒤 현재 주의 다음 내 시리즈가 있으면 `weekSchedule.fixtureId`만 바꿔 준비/정산을 반복하지 않는다. 해당 주 모든 시리즈가 끝났을 때만 `settling`과 마지막 하루 정산으로 넘어간다. 저장 검증은 회차 선후관계·동일 주간 경계·현재 시리즈/명단을 함께 확인한다. v38 이전에는 `ranked:null`만 보충하고 단계별 영수증을 함께 조회해 중복 보상을 막는다. [순위별 작업 기록](../work-logs/2026-11-13/2026-11-13-13-world-ranked.md).

## 세계 BO5 종료 — v40

`world-finals.js`는 순위별 진출4팀의 기존 고정 추첨 대진을 재사용해 `worldSeason.playoffs`를 구성하고 최종16팀의 공동순위를 계산한다. 기존 BO3 결과·저장 검증은 기본 선승2를 유지하고 세계 `world-final`에서만 선승3을 받는다. 기존 맵 선택으로 처음3맵을 정한 뒤 첫2맵을 반대 시작 진영·독립 시드로 반복한다. 결승 생성·다음 시리즈·공식 영수증·실제 AI 엔진도 기존 처리를 재사용한다.

세계 플레이오프의 주간 ID는 `world-1-playoffs`다. 준비·훈련 뒤 같은 주에 준결승·결승을 치르고 마지막 하루만 정산한다. 정산 중단 시 완료 BO5를 보존하며 정상/파산 정산 경로 모두 세계 시즌 종료 함수를 사용해 계약 종료를 한 번 처리한다. 관전·다음 맵·기권 경고는 BO3/BO5 길이에 따라 표시한다.

v40은 고정 대진/맵·3승 종료/기권·최대5맵·시리즈 선후관계·52주 일정·마지막 정산을 복원해 검증한다. 구버전에는 `playoffs:null`만 보충하고 과거 단계의 날짜/결과/명단/자금을 소급 변경하지 않는다. 기존 JSON 공백 축소와1MB 제한을 유지한다. [세계 BO5 작업 기록](../work-logs/2026-11-13/2026-11-13-14-world-finals.md).

## 자유 일정·영입 재개 — v41

`season-calendar.js`는 기존 실제 최종 순위/정산으로 올해 도전 종료를 판정한다. 국내 최종1·2위와 세계 단계 진출팀은 제외하고 세계 조별/순위별 탈락 또는 세계 플레이오프 정산 완료를 확인한다. 현재 단계의 공식 경기/일정·주간 잔여/이벤트·팀 훈련이 모두 끝난 뒤 `seasonCalendar.phase='offseason'`으로 전환한다. 이미 자유 일정에 들어간 뒤의 일반 주간 이벤트/훈련은 이 상태를 유지한다.

공식 결과/AI 결정전 완료·주간 정산/파산·팀 훈련 보상 완료에서 같은 종료 처리를 호출한다. 자유 일정에서는 공식 주간 생성과 시즌 스폰서 새 계약을 막고, 기존 영입 창구는 비시즌 또는 자유 일정에 연다. 세계 시즌 계약만 기본으로 정리하고 방송 계약·과거 정산·날짜/자금/능력은 보존한다. 주간 행동·재정 계산은 기존 함수를 재사용한다.

v41은 종료 근거 없는 자유 일정 위조와 공식 일정의 동시 존재를 거부한다. v40 이전에는 검증된 기존 결과와 현재 중단 상태로 전환 여부를 계산하며, 진행 중 일정은 먼저 보존한다. 새 해나 대진을 생성하지 않고 다음 해 전환 구현은 별도다. [작업 기록](../work-logs/2026-11-14/2026-11-14-01-free-schedule.md).

## 연도 보관·다시 시작 — v42

`seasonYears`는 현재 `year`·`startedDay`와 `archives`를 보관한다. 보관 연도에는 시작/종료일·종료 달력 상태·국내/세계 시즌과 공식 영수증만 넣으며600명 선수나 구단 재정을 복제하지 않는다. 기존 경기ID는 연도 묶음 내부에 보존한다. 영수증 중복 검증은 해당 연도에서 수행하고 누적 합산은 연도별로 각각 조회하므로 같은 로컬ID가 다음 해에 생겨도 보상을 누락하거나 과거에 다시 지급하지 않는다.

`season-year-context.js`의 대회 시드는1년 차 기존 세계 시드를 그대로 유지하고 다음 연도부터 세계 시드/연도에서 고정 파생한다. 이 시드를 기존 대진/맵/플레이오프 생성과 검증 양쪽에 적용한다. 선수 생성·구단 이름/로고·이벤트/행동·주식 난수는 바꾸지 않는다. 비시즌 종료일과 주차는 현재 연도 시작일에 상대적으로 계산한다.

`season-years.js`는52주 이후 자유 일정과 중단 상태/파산을 확인한 뒤 이전 시즌을 보관하고 현재 날짜에서 비시즌/PC방 미진행 상태를 만든다. 현재 날짜/선수/계약/재정/시설/주식은 유지하며 추가 일수나 정산을 처리하지 않는다. 저장 검증은 연도 순서·연속 경계·기간·완료 근거와 모든 보관 대진/맵/영수증을 기존 검증 함수로 다시 확인한다. 현재 영수증의 날짜가 지난 연도에 속하면 거부한다.

시즌 화면은 현재 경기와 지난 연도 조회를 구분하고 보관 경기에는 실행 버튼을 만들지 않는다. 구단/시즌의 새해 버튼은 같은 조건 판정을 사용한다. v41 이전에는1년 차/시작1일/빈 보관함을 추가하며32MB JSON 한도와 기존 포맷/데이터 검증을 유지한다. [작업 기록](../work-logs/2026-11-14/2026-11-14-02-season-years.md).
